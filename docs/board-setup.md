# 게시판 운영 적용

## 사용자 흐름

- 플랫폼 공용 비밀번호로 로그인 → 게시판 → 글쓰기.
- 작성자 이름, 제목, 본문, 분류, 글 비밀번호(8~128자)를 입력한다. 작성자 이름은 본인 인증된 이름이 아니다.
- 업무안내/자료실은 누구나 작성하며 공지사항 분류와 상단 고정은 관리자만 지정한다.
- 본문은 Markdown 기본 서식·미리보기를 지원한다. HTML 실행과 외부 이미지 삽입은 지원하지 않는다.
- 글 비밀번호는 scrypt 해시와 임의 salt로만 저장한다. 수정·삭제에 사용하고 조회 응답에 포함하지 않는다.
- 임시저장·게시 취소 글은 일반 목록/검색에 나오지 않는다. 저장 완료 화면의 관리 링크를 즐겨찾기한다.
  링크를 잃었거나 비밀번호를 잊었다면 관리자에게 요청한다. 자동 비밀번호 찾기는 없다.
- 파일은 PDF/HWP/HWPX/DOC/DOCX/XLS/XLSX, 글당 최대 3개·합계 3 MiB.
  파일 선택의 accept 속성뿐 아니라 서버가 확장자/기본 시그니처/전체 크기를 검사한다.
  문서 내용 검사나 바이러스 검사를 제공하는 것은 아니다. 파일은 서버에서 실행·미리보기하지 않는다.
- 일반 다운로드는 게시된 글의 첨부에 한한다. 임시글의 첨부 목록은 비밀번호 인증 편집 화면에 표시되며
  일반 작성자의 임시글 첨부 다운로드는 지원하지 않는다. 게시판 관리자는 비공개 상세에서도 다운로드 가능하다.
- 관리자는 게시판 하단 관리자 로그인 → 등록된 기존 계정 → 비공개 글 보기/수정/삭제/공지 고정.
  관리자 로그아웃 버튼은 기존 관리자 세션 쿠키도 종료한다.
- 기존 '아침에 읽는 규제변화'는 게시판 상단 바로가기로 유지한다.
- 게시된 글 상세 하단에서 댓글을 작성한다. 작성자 이름(1~40자), 내용(1~2,000자),
  댓글별 비밀번호(8~128자)가 필요하며 이름은 본인 인증된 이름이 아니다.
- 댓글은 최신순 20개씩 표시한다. 수정·삭제는 댓글 비밀번호로 확인하고 관리자는 기존 계정으로 처리한다.
  대댓글/첨부/알림/비밀번호 찾기는 지원하지 않는다. 댓글 본문은 일반 텍스트다.
- 글을 게시 취소하면 댓글도 보이지 않고 댓글 쓰기를 차단한다. 다시 게시하면 기존 댓글이 보인다.
  글을 물리 삭제하면 댓글도 함께 삭제된다. 댓글 자체 삭제도 복구 기능이 없다.

## 적용 순서

1. 운영 적용 전 해당 Supabase 프로젝트/기존 migration 상태를 확인한다.
2. DB 백업·변경 절차에 따라 `db/migrations/202610050001_board.sql`을 한 번 적용한다.
   기존 기사나 제재 테이블은 변경하지 않는다. 신규 테이블 2개, 제한 함수 1개, private Storage bucket/policy를 만든다.
   기존 게시판 migration이 이미 적용된 프로젝트에는 이를 다시 실행하지 않는다.
   댓글 적용에는 이후 `db/migrations/202610090001_board_comments.sql`을 한 번 적용한다.
   댓글 테이블·인덱스·게시 상태 검증 trigger를 추가하며 기존 글이나 제재/기사 행을 바꾸지 않는다.
3. Vercel의 대상 환경에 다음을 설정한다. 실제 값은 문서나 Git에 기록하지 않는다.
   - `BOARD_ENABLED=true`
   - 기존 선택 DB 설정: `NEXT_PUBLIC_USE_V2_DB`, 해당 `NEXT_PUBLIC_SUPABASE_URL[_V2]`
   - 서버 전용 `SUPABASE_SERVICE_ROLE_KEY`
   - 기존 `APP_PASSCODE`, `SESSION_SECRET`
   - 관리자 기능: Supabase Auth에 등록한 계정의 UUID를 `ADMIN_USER_IDS`에 쉼표로 구분한다.
     개인 이름이나 공용 글 비밀번호를 넣는 항목이 아니다.
4. 코드 배포 후 일반 세션으로 목록·작성·첨부 다운로드·틀린 비밀번호 거절·수정·임시저장·삭제를 확인한다.
   별도 관리자 계정으로 공지 고정/해제·비공개 조회·로그아웃을 확인한다.
   댓글 작성/목록/페이지 이동, 잘못된 비밀번호 거절, 수정/삭제, 게시 취소 후 비노출, 관리자 댓글 관리를 확인한다.
   이 개발 작업은 운영 migration이나 배포를 실행하지 않는다.
5. `BOARD_ENABLED=false`로 되돌리면 게시판 API 접근을 중단할 수 있다. 롤백 때문에 기존 글이나 bucket을 삭제하지 않는다.

게시판은 `INTERNAL_DOCUMENTS_ENABLED` 활성화나 내부 문서/제재 migration 없이 사용할 수 있다.
일반 이용에는 ADMIN_USER_IDS도 필요하지 않으며 관리자 로그인만 별도 설정이 필요하다.
코드의 `scope='documents'` 기본 관리자 경로는 기존 feature flag와 기존 rate-limit 함수 사용을 유지한다.

## 데이터 처리와 복구

- 게시글/임시글/비밀번호 해시/첨부 경로는 `board_posts`에 저장하고 anon/authenticated 직접 접근을 차단한다.
- 세션·Origin·권한 검증 후 서버만 접근한다. 서버 응답은 private/no-store이며 저장 경로/비밀번호 해시는 제외한다.
- 수정/삭제는 revision 조건으로 처리한다. 충돌 시 다른 저장을 덮어쓰지 않고 최신 글을 다시 열도록 안내한다.
- 글 삭제는 물리 삭제다. 비공개로 보관하려면 게시 취소·임시저장을 사용한다.
- 댓글은 board_comments에 저장하며 직접 클라이언트 DB 접근을 차단한다. 해시는 서버에서만 사용한다.
  댓글별 비밀번호 확인도 15분 10회 제한이다. 관리자는 비밀번호를 확인하지 않고 기존 계정 권한으로 처리한다.
  동시 수정 충돌 시 댓글 작성 내용을 복사해 보존하고 목록을 다시 열어 최신 revision으로 작업한다.
- 첨부 업로드 후 글 metadata를 원자 저장한다. 충돌하면 해당 요청이 새로 올린 파일만 정리한다.
  DB 통신 실패 시 commit 여부가 모호하므로 파일을 무조건 지우지 않는다.
  삭제/첨부 교체 후 Storage 정리가 실패해도 일반 사용자 다운로드는 즉시 차단된다.
- 필요 시 운영자가 `board_posts.attachments[*].path`와 bucket 객체를 비교해 미참조 객체를 점검한다.
  진행 중 업로드/실패 복구를 고려해 최소 24시간 유예하고 참조를 재확인한 뒤 수동 삭제한다.
  이 개발 작업에서는 운영 파일 정리나 DB migration을 실행하지 않는다.
- 쓰기 요청은 세션당 분당 30회·전체 분당 300회, 비밀번호 확인은 글당 15분에 10회로 제한한다.
  성공한 확인도 제한에 포함된다. 글별 제한 때문에 집중 시도 후 정상 작성자도 잠시 기다려야 한다.
  관리자 로그인은 별도 전체·이메일 제한을 적용한다. 원본 세션/IP/비밀번호를 rate-limit 테이블에 저장하지 않는다.

## 로컬 검증

`web/`에서 `npm test`, `npm run test:board-db`, `npm run test:documents-db`,
`npx tsc --noEmit --incremental false`, `npm run lint -- --no-cache`, `npm run build`를 실행한다.
테스트는 mock 및 PGlite만 사용한다. 실제 운영 API 키나 운영 DB가 필요하지 않다.
빌드는 기존 next/font Google Fonts 다운로드를 사용하므로 관련 네트워크 허용이 필요하다.
