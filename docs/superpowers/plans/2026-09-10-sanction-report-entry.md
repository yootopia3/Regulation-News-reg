# Report 하위 메뉴와 제재공시 조회

사용자 요청: 기존 Report 메뉴 안에 `재제공시 리포트` 하위 메뉴를 둔다.
표시명은 요청한 표기를 유지하고 경로는 `/reports/sanctions`로 한다.

## 이번 단계

Stage A 이후 운영 연결에는 Supabase 관리자 설정과 worker 실행 환경이 필요하다.
현재 로컬에서 해당 설정을 확인하지 못했으므로 운영 적용 완료로 표시하지 않는다.
그동안 일반 사용자 화면의 진입점과 실제 수집된 공시 조회를 먼저 연결한다.

1. 기존 Report 메뉴의 아침 리포트를 유지하고 새 링크를 추가한다.
2. 기존 인증된 `/api/articles`를 재사용한다. 제재 카테고리와 기관 코드가
   모두 일치하는 행만 별도 DTO로 변환한다. 내부 문서 API는 호출하지 않는다.
3. 제목 검색, 공시 종류 선택, 날짜순 목록, 공개 원문 열기, 기존 수집 요약을 제공한다.
   기존 API의 최신 1,000건 한계를 명시한다. AI 부서 매칭 결과로 표현하지 않는다.
4. 로딩/빈 결과/오류/세션 만료를 구분하고 재시도 및 로그인 이동을 제공한다.
5. 분석·게시 미연결 안내와 관리자 문서 관리 진입점을 둔다.
   관리자 문서 API의 독립 인증은 그대로 유지한다.
6. 메뉴·필터·URL·비공개 필드 제외·오류·로그인 경로를 테스트한다.
   별도 검토 pass 후 lint/build를 검증한다.

## 이어질 작업

운영 설정 및 문서 활성화, Stage B 공개 PDF 근거 추출/OpenAI 분석,
Stage C 관리자 검토/게시/내보내기는 기존 계획을 따른다.
현재 화면은 게시된 점검 리포트가 있는 것처럼 가짜 부서나 점검 항목을 만들지 않는다.

2026-09-10: 웹 전체 97개 테스트, ESLint 및 Next.js production build 통과.
별도 정적 코드 검토에서 수정이 필요한 결함 없음.
운영 DB 접속·배포·실제 AI 분석은 실행하지 않았다.
