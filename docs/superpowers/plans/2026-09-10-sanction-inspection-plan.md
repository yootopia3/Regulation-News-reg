# 제재 점검 기능 구현 계획

작성일: 2026-09-10
상태: Stage A 로컬 구현·검증 완료 / 운영 적용 전. Stage B 분석 라이브러리 추가,
PDF·DB 큐·관리자 웹 실행 연결 추가. Stage C 편집·게시·철회·일반 조회·XLSX 추가.
실제 운영 적용과 AI 품질 검증은 미완료.
설계: `docs/superpowers/specs/2026-09-10-sanction-inspection-design.md`

Stage A 구현 상세와 운영 준비: `docs/internal-documents-setup.md`.
구현에서는 업로드 전용 URL 대신 최대 2MB 파일을 관리자 서버 API로 받으며,
독립 `internal_document_jobs`를 사용한다. 작업/버전 범위와 비공개 원칙은 동일하다.

## 진행 원칙

- 아래 A/B/C는 의존성이 있는 작업 단위다. 각 단위마다 설계 확인→세부 계획→구현→검증→별도 검토를 수행한다.
- 합성 문서와 mock API로 먼저 구현한다. 실제 내부 파일을 저장소·공개 Actions·테스트 fixture에 넣지 않는다.
- 계획 작성은 운영 저장소 생성, API 호출, 유료 서비스 가입을 의미하지 않는다.
- 기존 `articles.analysis_result`에 내부 결과를 넣지 않는 원칙과 관리자 전용 문서 접근을 모든 단계에서 유지한다.

## A. 관리자 권한과 비공개 문서 관리

### 설계 확인

일반 passcode 로그인은 유지하고 Supabase Auth 기반 관리자 allowlist를 추가한다.
로컬에서 검증한 HWP 파서는 운영 라이선스·버전 적합성을 확인한 후 확정한다.
초기 HWP v5 지원과 관리자가 추출 결과를 확인한 뒤 활성화하는 흐름을 구현한다.

### 작업

1. `web/lib/auth.ts`와 별도 관리자 auth helper, 관리 로그인 페이지/API를 구성한다. 관리자 인증 상태를 기존 `mp_session`으로 대체하지 않는다.
2. `web/proxy.ts`의 광범위 정적 경로 예외를 좁히고, 모든 신규 관리 route에서 인증·권한을 다시 확인한다.
3. `db/migrations/`에 private 문서·업무 단위·job·event 테이블 및 명시적인 grants/RLS를 작성한다. 운영 schema와 대상 프로젝트는 적용 전에 확인한다.
4. `web/lib/` 서비스에 document 등록·상태·검토·활성화·폐기 기능을 분리한다. 관리자 `/admin/documents` 화면은 이 서비스를 호출한다.
5. `src/services/` 아래 문서 처리 모듈과 worker 진입점을 추가한다. 공통 DB 접근은 `src/db/client.py`를 재사용하고 내부 작업은 service-role 필수로 한다.
6. 서명 확인, 용량 제한, 압축해제 제한, 조문/업무/참조 보존, 미분류 경고를 구현한다. 원본 문서의 내용은 오류에 포함하지 않는다.
7. 문서 해시 중복 처리, 작업 lease·재시도, 새 버전 활성화와 구버전 처리, 임시 파일 정리를 구현한다.

### 검증 및 별도 검토

- pytest: 합성 조문, 중복/누락, 부칙·목차, 삭제 조문, 하위 업무, 참조, 손상 파일, 암호화 파일, 대용량 압축.
- vitest: 일반/관리자/위조/만료 세션, 직접 URL 접근, CSRF, 업로드 위조, 문서 버전 충돌.
- 격리 DB/Storage: anon·일반 authenticated·미허용 관리자 계정의 직접 read/write/list/download 거부.
- 승인된 실제 문서의 관리자 검토 화면에서 기존 5개 표본과 추가 예외 구간을 확인한다.
- 별도 review lane: 관리자 인증 누락, service-role 오용, worker 로그/파일 노출 검사 후 다음 단계로 이동.

## B. 공개 제재 PDF와 내부 업무의 연결

### 설계 확인

기존 수집과 Gemini 분석을 유지하며, 새 점검 작업만 별도 OpenAI 경로로 처리한다.
API 계정이 준비되지 않았을 때는 mock으로 개발하고 실제 내부 전송은 실행하지 않는다.

### 작업

1. `src/collectors/`의 기존 첨부/HTTP 경로를 확인하고 공개 PDF 가져오기 helper를 확장한다. 허용 호스트, IP/redirect 검사, 응답 크기 제한을 추가한다.
2. 페이지별 추출·해시를 보존하고 무텍스트 PDF는 OCR 필요 상태로 처리한다.
3. `src/services/analyzer/`의 기존 mapper/설정 패턴을 참고해 점검용 구조화 결과와 전용 OpenAI 호출 모듈을 추가한다. Gemini wrapper를 복제하거나 내부 데이터 fallback 대상으로 사용하지 않는다.
4. 활성 문서에서 업무 후보를 검색하는 서비스를 작성한다. 전체 데이터 로딩은 1000행 페이지네이션을 지키고, 상위 부서와 관련 참조를 유지한다.
5. 지적사항별 부서 ID·근거 ID·점검 질문·증빙을 반환하도록 분석한다. 존재하지 않는 ID, 근거 없는 확정, 과도한 원문 재현을 검사한다.
6. 비공개 inspection/item 테이블에 초안과 분석 버전을 기록한다. 캐시 키는 PDF와 활성 문서 버전 집합, 모델/프롬프트 버전을 반영한다.
7. 관리자만 생성할 수 있는 멱등 job API, 상태 조회, 재시도, 안전한 실패 안내를 구현한다.

### 검증 및 별도 검토

- mock OpenAI: `store: false`, 선택된 텍스트만 전송, 기능 OFF 시 호출 0회, 공급자 자동 fallback 없음.
- PDF 다중 지적사항, 페이지 근거 일치, 추출 실패 시 성공 오표시 금지.
- 후보 부서/근거 ID 검증, 미매칭 시 확인 필요, 교차 참조, 문서 교체 시 캐시 무효화.
- 악성 PDF URL·리다이렉트·사설 IP·prompt injection·장문 원문 유도 테스트.
- 같은 요청 동시 실행, lease 회수, 제한된 재시도, API timeout/429/5xx 처리.
- 별도 review lane: 전송 payload, 저장 위치, 로그, ID 검증과 실패 경로 검사.

## C. 검토·게시와 일반 사용자 결과 화면

### 설계 확인

일반 사용자는 게시된 분석 결과만 조회한다. 관리자에게만 내부 근거와 생성·수정·게시를 제공한다.
게시 직렬화는 허용 목록 방식으로 수행하고, 관리자 검토를 건너뛰어 AI 원문을 사용자에게 반환하지 않는다.

### 작업

1. `web/lib/validation/`와 서비스 계층에 초안/관리자/게시 DTO를 각각 정의한다.
2. 관리자 검토 화면에 제재 지적사항·원문 PDF 페이지·부서 후보·내부 근거·점검표를 표시한다.
3. 관리자 수정 이력과 revision 충돌 검사를 구현하고, 게시 snapshot 및 철회 흐름을 추가한다.
4. 제재 상세의 일반 사용자 화면은 게시본만 읽게 하고, 내부 파일명/인용/객체 키를 반환하지 않는다.
5. 게시본 기반 XLSX 내보내기를 구현한다. 내부 근거·숨김 데이터·수식 주입이 없는지 검증한다.
6. 문서 버전이 바뀐 결과의 구버전 상태, 빈 결과, 준비 중, 실패, 재검토 안내를 추가한다.
7. 실제 schema와 구현 완료 결과에 맞춰 `docs/SCHEMA.md`, `ARCHITECTURE.md`, `REQUIREMENTS.md`를 갱신한다. as-built 문서를 구현 전 사실처럼 바꾸지 않는다.

### 검증 및 별도 검토

- 일반 API·내보내기·에러·클라이언트 상태에 내부 원문/근거/미게시 결과가 없는지 합성 canary로 검사한다.
- 관리자 역할 제거, 미게시/철회/구버전 결과, 직접 export URL, 로그인 없는 접근 검사.
- 게시 DTO 필드 검증뿐 아니라 문자열 내부의 인용 유출도 검사하고 관리자 게시 확인을 검증한다.
- 테스트 대상: `pytest tests/`, `web`의 `npm test`, `npm run lint`, `npm run build`; 필요한 환경변수는 fixture로 주입한다.
- 실제 업무 사례의 담당자 평가: 지적사항 누락, 부서 후보 오류, 근거 불일치, 실행 불가능한 점검 질문을 기록한다. 5개 문서 표본 확인과 AI 품질 평가는 별개다.
- 별도 review lane 완료와 발견 사항 해결 후 배포 단계로 이동한다.

## 배포 순서와 운영 검증

1. 대상 Supabase/배포 프로젝트를 확인하고 migration·private bucket·관리 계정을 준비한다.
2. 서버 secrets는 안전한 설정 경로에서 주입한다. 모델·데이터 공유 opt-in·보관 정책을 확인하고 확인 날짜를 내용 없는 운영 기록에 남긴다.
3. worker 실행 위치, 지원 Python/파서, 용량·timeout·작업 비용 상한을 확정한다.
4. 기능 OFF 상태로 서버와 worker를 배포하고 합성 문서로 권한/Storage/API 검사를 수행한다.
5. 허용된 실제 문서를 관리자 화면에서 등록·검토·활성화하고 공개 제재 한 건을 분석한다.
6. 관리자 검토 후 게시하고 일반 세션으로 게시 결과와 내보내기를 확인한다.
7. 기능 플래그 OFF 및 worker 정지로 신규 처리·신규 화면 노출을 차단할 수 있게 한다. 롤백 시 기존 기사는 유지하며 민감 데이터를 공개 테이블로 이동시키지 않는다.

## 아직 확정하지 않은 항목

- OpenAI 계정의 실제 데이터 공유 설정, 사용 가능 모델, 키, ZDR 승인 여부.
- 관리자 계정과 allowlist, 운영 worker 서비스/요금, HWP 파서 배포 적합성.
- 운영 DB 권한과 bucket 상태; 기존 문서만으로 live 보안을 보장하지 않는다.
- 스캔 PDF OCR, 의미 검색은 최초 평가에서 필요성이 확인되면 별도 설계한다.

이 항목들은 운영 활성화 전에 필요하다. 합성 데이터 기반 구현 계획·개발을 막는 사유는 아니다.
